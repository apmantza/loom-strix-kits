# gfx1151: AMD Strix Halo (Ryzen AI Max+ 395, Radeon 8060S, RDNA 3.5)

Measured or verified on one box (128 GB LPDDR5X, Linux, Loom 0.2.0, Nov 2026) unless marked. A fact here holds for this target;
write a new file for another target instead of assuming RDNA 3 family behaviour.

## Limits used as floors (common/ceiling.py reads them from kits/<kit>/lanes.json)
- DRAM: ~216 GB/s measured streaming read in our kernels; 228 GB/s used as the practical decode floor; strix-halo-engine-lab
  measured 235-236 GB/s pure reads on the same chip.
- f16 WMMA: ~45 TFLOP/s clock-adjusted under real data (constant operands raise clocks and overstate it).
- BIOS power mode matters: on one board the 85 W default capped real-data WMMA at 43.8 TFLOP/s against 48.4 in the 120 W mode
  (loom-skills' KB, measured on a GMKtec box). Record the mode with every prefill number.

## Execution model
- No hardware async global->LDS copy on gfx11: prefetch is registers only, and the register allocator decides whether a
  prefetched load stays in flight (ROCm/hrx-system#3409). Check `s_waitcnt vmcnt` placement in the disassembly.
- VALU and WMMA do not overlap: dequant VALU inside a GEMM tile competes with the MMAs.
- Spills and global loads share `vmcnt`: any spill drains the prefetch.
- VOPD dual issue is rare in generated code (8-12 % of VALU ops paired in our attention loops); single-issue v_mov copies from
  the allocator (#3542) and v_cndmask guards are the usual bulk.
- Loom on gfx11 has no cache-policy hints (non-regular policies are dropped with a remark), no `view.prefetch` (gfx12), no async
  copy, split barriers fall back to full barriers, and no VGPR cap or occupancy request.

## Serving with Loom
- loom-serve needs unlimited memlock (io_uring pinning): `ulimit -l unlimited` or DefaultLimitMEMLOCK=infinity.
- Pool backing: `--pool_backing=fixed` ties elastic on speed here; an 8-bit KV cache corrupted only under elastic backing in
  0.2.0, and elastic needs power-of-two text-cache pages (16,640-byte pages faulted the GPU).
- Unified memory: the GPU's share (GTT) is invisible to MemAvailable; read it from /proc/PID/fdinfo (common/checks.py drm PID).

## Profiling
- Per-dispatch device time: loom-serve `--device_profiling_mode=dispatch-events,executable-metadata --device_profiling_output=X`,
  exported with an `iree-profile` built from the installed hrx-system tag (common/events_ab.sh).
- Hardware counters: Loom's runtime drives /dev/kfd itself (no HSA), so rocprofv3 / rocprof-compute see no Loom kernel, and Loom
  0.2.0 / 0.3.0 implement no GPU hardware counters. Launch the served code object through HIP instead and profile that:
  ROCm 10.2 (Nov 2026) in a venv: `pip install --index-url https://stable.repo.amd.com/rocm/whl-next/ "rocm[profiler,devel,device-gfx1151]==10.2.0"`
  (link `libamdhip64.so` and `libhsa-runtime64.so` to their versioned files in `_rocm_sdk_core/lib`), then
  `LD_LIBRARY_PATH=<venv>/lib/python3.12/site-packages/_rocm_sdk_core/lib <rocprofv3> --pmc ... --kernel-trace -- <harness>`.
  The old per-family index (repo.amd.com/rocm/whl/gfx1151/) stops at 7.13, which offers 38 counters on gfx1151 and no wait
  reasons; 10.2 offers 263, a superset, including SQ_WAIT_{CNT_VMVS,CNT_LGKM,DELAY_ALU,INST_LDS,BARRIER,...},
  SQ_INST_LEVEL_TEX_LOAD (loads in flight), GL2C_EA_RDREQ_DRAM and GCEA_RDRAM_* (DRAM requests). That the new counters
  read correctly on gfx1151 is still to be shown on a run. Its release notes tie thread-trace and PC-sampling changes to
  other families only: test before relying on them. Trusted counts need `power_dpm_force_performance_level=profile_standard`
  (root; restore `auto`): automatic power mode gates some perfmon clocks on RDNA3.
- AMD's apt ROCm repository publishes for Ubuntu 22.04 / 24.04 only (checked Nov 2026); on newer releases keep the distribution's
  ROCm (llama.cpp's HIP build links it) and put newer tools in a venv.
