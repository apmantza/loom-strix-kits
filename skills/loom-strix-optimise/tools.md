# Tools by step of the work

Search this list, Loom's own tools (`loom-*`, their `--help`, the docs' workflows), installed Python packages and the ROCm
and llama.cpp builds before writing a tool: a hand-written remote header reader, a hand-derived bank analysis and a planned
KL-divergence path each turned out to exist already (rules.md section 2). Add a tool here only with the step that uses it.

**Pending verification** (listed so they are tried, not yet steps; each moves into the table with the row that verifies it):
- 3, 6 IR-level ablation and pass bisect: `common/ir_trace.py ablate | bisect` (pending merge of ir_trace.py; HRX-like E537): deletes or
  moves one prepared-Low op and reassembles it against an unedited control; names the first pass at which a predicate on IR or
  disassembly holds. Limits: reassembled prepared Low does not reproduce the default pipeline's binary on 0.2.0 (flash2: 4,805 vs
  4,808 reassembled instructions, +2 s_waitcnt, +1 s_delay_alu; confirmed by an independent review, not a tool flag: HRX-like E543), and waits, `s_delay_alu` and register choice are placed at emission, after the last pass, so no IR edit or bisect reaches them.
- 7 Correctness: `loom-test --sanitizer=race` (LDS races between barriers; accepted by loom-compile 0.2.0 though its help lists only
  access / value / operation) and `--sanitizer=access` (bounds on every view access: the padding-overrun class), with
  `--sanitizer-reporting=report-only`. Compiles on gfx1151 (HRX-like E530); not yet run on the GPU (a queued step).
  loom-serve applies no sanitizer.
- 1 One kernel in a served profile: loom-serve `--device_profiling_filter_function=GLOB` (heavy artifacts such as dispatch timings only
  for matching functions; cheap metadata stays so the capture decodes). Its 0.2.0 parser accepts it (checked 11-25: an unknown spelling
  is refused, this one is not); whether the capture and iree-profile's export work on gfx1151 is unverified (needs the GPU).
- 8 Schedule search: `--config=` bindings over `pipeline(%depth) unroll(%factor)` instances, compiled as a bounded grid and ranked by
  report before any GPU run (hrx-system loom/docs/src/workflows/search-loop-schedules.md, tune-loop-schedules.md); under test on a
  branch. common/autotune.py covers env-knob grids of our generators today.

**Loom's oracle workflows** (step 5, prior art; hrx-system loom/docs/src/workflows/oracles/, methods none of which has run here):
- ggml-llama-cpp.md: which llama.cpp kernel, grid and dispatch order did the production run actually select for this shape, and what
  GGUF / GGML contract (format, op semantics) must a Loom port match before scores are compared?
- radv.md: what native program did the Vulkan driver (RADV) compile for one exact dispatch (pipeline executable properties or
  pipeline binaries), as a performance reference and a compiler oracle beside Loom's own Vulkan and AMDGPU paths?
- llvm-mc.md: does LLVM encode the same bytes as Loom for these instruction packets (target selection and encoding only, not
  semantics or speed)?
- native-schedule.md: can a native schedule (hand assembly, a vendor library, another compiler) run through Loom as prepared Low
  (`loom-run --pipeline=none`), and where does the default pipeline first diverge from it on the way to maintained source?
- pytorch.md (0.3.0 docs only): how to capture a PyTorch module's inputs and outputs at one boundary and replay them as a Loom
  correctness case.

Not useful here: `llvm-mca` (no gfx1151 scheduling model), rocprof against loom-serve or loom-benchmark (sees nothing).
